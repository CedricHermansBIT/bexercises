# BITLab MCP for Codex

BITLab exposes a stateless Streamable HTTP MCP endpoint at `/mcp` (also
`<BASE_PATH>/mcp` for subdirectory deployments). It runs inside the existing
BITLab server and uses the same database, runtimes, grading and execution queue.
Codex supplies the AI generation; BITLab does not need an OpenAI API key.

## Enable on the BITLab server

Install the dependencies with `npm ci`. Generate a dedicated secret:

```sh
openssl rand -hex 32
```

Put the result in the server's `.env`, and specify the hostname that clients use:

```dotenv
BITLAB_MCP_TOKEN=replace_with_generated_secret
BITLAB_MCP_ALLOWED_HOSTS=localhost,127.0.0.1,bitlab.example.edu
```

Restart BITLab. Without a token the endpoint returns 404. Tokens shorter than
32 characters prevent startup. Requests require `Authorization: Bearer <token>`;
browser sessions do not grant MCP access. Hostnames are checked independently of
proxy headers. Configure the proxy to preserve an allowed Host header. Browser
Origin headers are rejected; this endpoint is intended for MCP clients.

Use HTTPS for remote connections. The token allows exercise and fixture authoring
and reference-solution access; share it only with trusted instructors. Rotate it
by replacing the server value, restarting, and updating the clients. No student
accounts, statistics, grades, exam uploads or deletion tools are exposed.

## Connect Codex

Export the same token in the environment where Codex runs, using your secret
manager or terminal setup. Do not put the literal token in a repository:

```sh
export BITLAB_MCP_TOKEN='the_same_secret_as_the_server'
```

Add this to `~/.codex/config.toml` (or your project Codex configuration):

```toml
[mcp_servers.bitlab]
url = "https://bitlab.example.edu/mcp"
bearer_token_env_var = "BITLAB_MCP_TOKEN"
startup_timeout_sec = 20
tool_timeout_sec = 600
```

For a local server use `http://localhost:3000/mcp`. Include your deployment base
path if needed, for example `https://example.edu/bitlab/mcp`. Restart your Codex
session and check `/mcp` or `codex mcp list`.

Configuration follows the [official Codex MCP documentation](https://developers.openai.com/codex/mcp/).
The transport uses the [official MCP TypeScript SDK](https://ts.sdk.modelcontextprotocol.io/server).

## Tools

| Tool | Purpose |
| --- | --- |
| `bitlab_list_languages` | Runtime IDs, interpreter/image settings and starter templates |
| `bitlab_list_chapters` | Chapters for a language |
| `bitlab_list_exercises` | Summaries, optionally filtered by language/chapter |
| `bitlab_get_exercise` | Complete exercise, solution and tests |
| `bitlab_list_fixtures` | Fixture names, types, sizes and permissions |
| `bitlab_get_fixture` | Existing text fixture content, up to 256 KiB |
| `bitlab_create_fixture` | New UTF-8 fixture, up to 256 KiB; never overwrites an existing file |
| `bitlab_test_exercise` | Generate and verify tests for an unsaved exercise; optionally grade a candidate script |
| `bitlab_run_exercise` | Grade a candidate or the reference against a saved exercise |
| `bitlab_save_exercise` | Create/update a live exercise after generating and verifying expected outputs |

Runner tools use the shared execution queue and MCP run quota (`RUNS_PER_MINUTE`,
default 6). They do not record submissions or modify student progress. A busy
queue or exhausted quota returns a tool error; retry later rather than launching
parallel retries.

Saving requires `mode: "create"` or `"update"`, plus the complete exercise:

```json
{
  "mode": "create",
  "exercise": {
    "id": "save-listing",
    "title": "Save a directory listing",
    "language_id": "linux-basics",
    "chapter": "Chapter 5 - Input and output",
    "description": "Save the long directory listing to `listing.txt`.",
    "solution": "#!/bin/bash\nls -l > listing.txt\n",
    "testCases": [{
      "arguments": [],
      "input": [],
      "fixtures": [],
      "outputFiles": ["listing.txt"],
      "useDynamicOutput": true
    }]
  }
}
```

Use IDs from `bitlab_list_languages`; the example assumes `linux-basics` exists.
Test inputs accept `arguments`, `input`, `fixtures`, `outputFiles`,
`useDynamicOutput` and `validationQuery`. Expected stdout, stderr, exit codes,
file states and validation outputs are generated by BITLab, not trusted from the
model. For updates, provide all test inputs; omitted tests are not retained.
The order is preserved on updates unless explicitly provided.

Save refuses a broken reference or missing output paths. It generates expected
values and runs the reference against them before writing. Directory listings
should use dynamic output so the runner script stays outside the working
directory and file hashes are regenerated. Independent random values or timestamps
that change between executions may still differ; use controlled fixtures and
inputs to make tests reproducible.

There is no draft/publish system: `bitlab_save_exercise` immediately creates or
updates a student-visible exercise. `bitlab_test_exercise` leaves the exercise
unsaved, but creating a fixture writes it to the shared fixture catalog.

## Example requests to Codex

> Use BITLab to inspect the Linux basics language and its I/O chapter. Generate
> three beginner questions about redirection, each with a reference solution,
> positive tests and an intentionally incorrect candidate. Test them without
> saving and show me the proposed descriptions and results.

> Save those verified questions to BITLab. Keep their IDs distinct from existing
> exercises. Use dynamic file grading for directory listings.

> Load redirect-output, improve its explanation and add an existing text fixture
> to its tests. Preserve its language, chapter and existing test cases. Verify the
> reference, check an incorrect submission fails, then update it.

## Verification

```sh
npm test
RUN_CONTAINER_TESTS=1 node --test src/tests/mcp.test.js
```

The container test connects through the real MCP SDK, creates and edits exercises
in an in-memory database, grades scripts with Docker/Podman, and checks that no
student progress or attempts were recorded.
